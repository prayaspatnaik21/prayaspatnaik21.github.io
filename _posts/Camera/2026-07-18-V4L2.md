## Device discovery and Linux media architecture

### Check the Jetson Linux release

```bash
cat /etc/nv_tegra_release
```

1. This shows the NVIDIA Jetson Linux software release installed on the device.

### List the V4L2 devices

```bash
v4l2-ctl --list-devices
```

1. The command shows every device registered with the V4L2 subsystem and the `/dev` nodes associated with each device.
2. V4L2 is the Linux kernel interface used by applications to communicate with video-related hardware such as USB cameras, CSI cameras, and capture engines.
3. A camera application does not normally communicate directly with the sensor's electrical signals.
4. The rough path is: sensor → driver → V4L2 kernel interface → `/dev/video0` → application.
5. `v4l2-ctl` is a userspace command-line utility that can:
    - List video devices.
    - Query capabilities and controls.
    - List pixel formats.
    - Configure resolutions, exposure, and gain.
6. `--list-devices` provides:
    - A human-readable device or driver name.
    - The device nodes associated with it, such as `/dev/videoX` and `/dev/mediaX`.
7. `/dev/mediaX` describes relationships between components in a video pipeline.
8. One physical camera does not always expose only one `/dev/videoX` node. It may expose several interfaces.

### What is a device node?

1. Linux represents many hardware interfaces as special files under `/dev`.
2. Video capture interfaces may appear as `/dev/video0`, `/dev/video1`, and so on.
3. These device nodes act as entry points into kernel drivers.
4. When an application opens a node with `open()`, it requests communication with the associated kernel driver.
5. The application can then send V4L2 commands using `ioctl()` calls.

### What happens when `v4l2-ctl --list-devices` runs?

1. `v4l2-ctl` searches the Linux video-device information.
2. It finds registered V4L2 device nodes.
3. It queries their driver and card names.
4. It groups related nodes and prints the result.
5. The nodes exist because:
    - The camera driver loads.
    - The driver registers with V4L2.
    - Linux creates a node such as `/dev/video0`.
    - `v4l2-ctl` discovers that node.
6. If a connected sensor fails to probe, it may not appear as a usable V4L2 capture device.
7. A missing `/dev/videoX` can mean the camera pipeline is not fully registered. Possible causes include a driver that did not load or a sensor that was not detected over I2C.
8. If `/dev/videoX` appears, Linux has created a V4L2 video-device node.

## Inspecting the capture node

```bash
v4l2-ctl -d /dev/video0 --all
```

1. This opens `/dev/video0` and inspects its identity, capabilities, current configuration, format, and controls.
2. The utility sends V4L2 IOCTL requests to the kernel driver and formats the returned information.
3. For my Arducam IMX477, the current capture format was:
    - Width and height: 4032 × 3040.
    - Pixel format: `RG10`—10-bit Bayer RGRG/GBGB.
    - Field: none.
    - Bytes per line: 8064.
    - Image size: 24,514,560 bytes.
    - Colorspace: sRGB.
    - Transfer function: default, mapped to sRGB.
    - YCbCr/HSV encoding: default, mapped to ITU-R 601.
    - Quantization: default, mapped to full range.
    - Flags: none.
4. The streaming parameters reported:
    - Capability: `timeperframe`.
    - Frame rate: 21 FPS.
    - Read buffers: 0.

## Inspecting the media topology

```bash
media-ctl -d /dev/media0 -p
```

1. This command maps the Jetson camera pipeline.
2. It shows:
    - Which camera-related components Linux registered.
    - How the components are connected.
    - The direction in which image data flows.
    - Which components represent the IMX477 sensor, CSI receiver, and capture output.

### Reading the media graph

1. The Media Controller API represents the pipeline as a graph:
    - Entities are components.
    - Pads are input or output connection points.
    - Links connect a source pad to a sink pad.
2. An `[ENABLED]` link is active in the media graph, and data travels along that route.
3. Entity numbers such as 1, 4, 7, and 9 are identifiers assigned by Linux. They do not describe the order of image flow.
4. The node order is not `/dev/v4l-subdev0` → `/dev/v4l-subdev1` → `/dev/v4l-subdev2` → `/dev/video0`.

### The active IMX477 path

```text
Entity 7: IMX477 sensor (/dev/v4l-subdev2)
                    ↓
Entity 4: NVCSI (/dev/v4l-subdev1)
                    ↓
Entity 9: VI output (/dev/video0)
```

1. Entity 1, `/dev/v4l-subdev0`, has no active links and is not part of this IMX477 path.
2. Entity 7 represents the physical IMX477 sensor:
    - Its source pad sends data to the sink pad of Entity 4.
    - `9-001a` identifies I2C bus 9 and address `0x1a`.
    - The sensor is controlled through I2C but sends image data through MIPI CSI-2.
    - `SRGGB10_1X10` is the media-bus format: RGGB Bayer data with a 10-bit sample for each pixel.
    - The `/dev/video0` format and `bytesperline` describe how the driver stores that data in memory.
3. Entity 4 represents the active NVCSI receiver:
    - Its sink pad receives data from the IMX477.
    - Its source pad sends data to the VI capture output.
    - NVCSI receives the serialized MIPI CSI-2 stream and forwards the pixel data toward the capture engine.
4. Entity 9 represents the final V4L2 capture node:
    - It receives data from Entity 4.
    - Applications open `/dev/video0` to capture frames.
    - The Tegra VI capture hardware receives image data from NVCSI and writes frames into memory buffers.

## V4L2 subdevices and the capture node

1. The IMX477 is represented by `/dev/v4l-subdev2` and categorized as a camera sensor.
2. A V4L2 subdevice represents an internal component rather than the complete video-buffer interface.
3. Linux exposes subdevice nodes so userspace can discover or configure individual parts of the media topology.
4. `/dev/video0` is the final capture interface used by the application.
