# Set Up

1. Device Discovery and Linux Media Architecture

1. cat /etc/nv_tegra_release

    1. shows the NVDIA Jeton Linux Software Release installed on the jetson device.

2. v4l2-ctl --list-devices

    1. shows every device currently registered with V4L2 subsystem and shows the /dev device nodes associated with each one.
    2. V4L2 - linux kernel interface used by applications to communicate with video related hardware such as USB cameras , CSI camera , camera capture engines etc.
    3. Camera application does not normally communicate directly with the camera sensor's electrical signals.
    4. Rough path Sensor -> Driver -> V4L2 Linux Kernel interface -> /dev/video0 -> Application
    5. v4ctl is a command line application that communicates this v4l2 interface.
        1. It is a userspace utility.
        2. It can let you list video devices , query camera capabilities , list pixel formats , set resolutions , exposures , gains etc.
    6. --list-devices provides two inforamtion 
        1. Human readable device or driver name
        2. device nodes associated with that device /videoX /mediaX
        3. /dev/mediaX describes relationships between components in a video pipeline.
    7. One physical camera does not always give only one /dev/videoX.It may expose several interfaces.

3. What is a device node?

    1. Linux represents many hardware interfaces as special files under /dev.
    2. A video capture interface may appears /dev/video0 , /dev/video1 etc.
    3. These are called device nodes.They are like entry points into kernel drivers.
    4. when an application opens this file using open() function. It tries to request communication with the kernel driver associated with that particular device node. The application can send v4l2 commands using ioctl() calls.

4. what happens internally when the command runs?

    1. High level flow 
        1. v4l2-ctl searches linux video device information.
        2. Finds registered v4l2 device nodes.
        3. queries their driver and card names and groups related nodes together.
        4. print the results.
        5. The device exist because kernel drivers registered them with the V4L2 framework
            1. Camera Driver loads.
            2. Driver registers with V4L2.
            3. Linux creates /dev/video0
            4. v4l2-ctl discoves /dev/video0
        6. If a sensor is physically connected but the driver failed to probe , it may not appear as a usable v4l2 capture device.

    2. if there is no /dev/videoX , it can indicate that the camera pipeline is not fully registered. There are many possible reasons for this . Sensor driver didn't load or sensor was not detected over I2C etc.

    3. if /dev/videoX appears , it means Linux has created V4L2 video device nodes.

5. v4l2-ctl -d /dev/video0 --all

    1. opens the device node /dev/vidoe0 and shows the current configuration , capabilities , identity and controls of the device.
    2. It's more of an inspection command.
    3. Flow
        1. opens /dev/video0 
        2. send V4L2 ioctl requests
        3. kernel v4l2 driver receives them
        4. kernel returns driver information
        5. format and print out the results.

    4. Media Controller API represents the pipeline as a graph containing:
        1. Entities = components
        2. Pads = input/output connection points
        3. Links = connection between components.
            1. Connects one entity's source pad to another entity's sink pad.
            2. When link says``` [ENABLED] ``` , the connection is active in the media graph.
            3. Data travels along this route. 
        4. The Linux Media controller API lets application discover these entities , pad , link while V4L2 subdevices represent individual components such as sensors and bridge devices.
        5. ``` Quick info - the order is not subdev0 -> subdev1-> subdev2 -> /dev/video0 ```
        6. Entity 1 , 4 , 7 , 9 are just identifiers assigned by the linux.They do not describe the image flow.
        7. Actual Flow
            1. IMX4777 9 - 001a Entity 7 
            2. Active NVCSI - /dev/v4l-subdev1 Entity 4
            3. VI - output , imx477 9 - 001a - /dev/video0 Entity 9
            4. Entity 1 is not connected to the camera path.
        8. An Entity is one component in the camera pipeline eg sensor , CSI Receiver , capture outptut.
            1. Represents one funcitonal component of the media pipeline.
        9. Each component get its entity number.
            1. Entity 1
            
                ```
                - entity 1: 13e00000.host1x:nvcsi@15a00000- (2 pads, 0 link)
                type V4L2 subdev subtype Unknown flags 0
                device node name /dev/v4l-subdev0
                pad0: Sink
                pad1: Source
                ```

                1. This represents an NVDIA CSI receiver path.
                2. It has pad 0 and 1 . 0 corresponds to sink and 1 to source.
                3. One pad is responsible for receiving data and one for sending.
                4. It says 0 link so nothing is connected to this entity for now.
                5. No incoming data and outgoing data.
                6. This is not part of your active IMX477 path.
            
            2. Entity 4

                ```
                - entity 4: 13e00000.host1x:nvcsi@15a00000- (2 pads, 2 links)
                type V4L2 subdev subtype Unknown flags 0
                device node name /dev/v4l-subdev1
	
                pad0: Sink
		            <- "imx477 9-001a":0 [ENABLED]
	            pad1: Source
		            -> "vi-output, imx477 9-001a":0 [ENABLED]
                ```

                1. Active CSI receiver entity.
                2. Its sink pad receives data from imx477 9 - 001.
                3. IMX477 -> Entity 4 pad 0
                4. It's source pad sends data to the VI capture output
                    1. Entity 4 pad 1 -> /dev/video0
                5. Entity 4 sits in the middle and the device node - /dev/v4l-subdev1
                6. what is NVCSI?
                    1. Sensor sends image data using MIPI CSI-2.
                    2. That CSI-2 transmission travels over physical data lanes.
                    3. NVCSI receives the serialized CSI-2 stream and handles camera - interface responsibilities such as receiving and interpreting the CSI packet stream before forwarding pixel data towards the capture engine.
            3. Entity 7

                ```
                - entity 7: imx477 9-001a (1 pad, 1 link)
                type V4L2 subdev subtype Sensor flags 0
                device node name /dev/v4l-subdev2
	            pad0: Source
		        [fmt:SRGGB10_1X10/4032x3040@1/21 field:none colorspace:srgb]
		        > "13e00000.host1x:nvcsi@15a00000-":0 [ENABLED]
                ```

                1. Physical IMX477 image sensor entity.
                2. It has one pad which is a source one. It sends data.
                3. Pad 0 of Entity 7 sends data to the pad 0 of the Entity 4.
                4. Devide node for Entity 7 is /dev/v4l-subdev2
                5. ``` 9 - 001a ``` - identifies the sensor's I2C location
                    1. 9 -> I2C bus or adapter name
                    2. 001a -> I2C address
                    3. IMX477 is controlled over I2C bus 9 at address 0x1a.
                6. Sensor is controlled through I2C but sends images through MIPI CSI-2
                7. Sensor Format
                    1. ``` [fmt:SRGGB10_1X10/4032x3040@1/21 field:none colorspace:srgb] ```
                    2. SRGGB10_1X10 - media bus format code
                    3. It describes the format passing between hardware components inside the media pipeline.
                    4. RGGB - Bayer Filter Pattern , 10 - RAW bit depth
                    5. 1x10 - 1 pixel 10 bit information.
                    6. ``` /dev/video0 ``` capture format and bytesperline tell you how the driver stores that data in memory.
            4. Entity 9

                ```
                - entity 9: vi-output, imx477 9-001a (1 pad, 1 link)
                type Node subtype V4L flags 0
                device node name /dev/video0
                pad0: Sink
                <- "13e00000.host1x:nvcsi@15a00000-":1 [ENABLED]
                ```

                1. Final V4L2 capture node.
                2. It receives data from entity 4 pad 1, the NVCSI receiver.
                3. This is the node the Application open to get the data.
                4. It is the endpoint of the media controller topology.
                5. The tegra VI/Capture hardware receives image data from NVCSI and writes captured frames into memory buffers.
                6. NVCSI -> VI Capture Enginer -> DMA transfer -> Memory buffers -> /dev/video0

    5. v4l2 - subdev2

        1. IMX477 is represented by a V4L2 subdevice and is explicitly categorized as a camera sensor.
        2. A V4L2 subdevice represents an internal component rather than the full video buffer interface.
        3. Linux exposes subdevice nodes so userspace can discover or configure individual parts of the media topology.
        3. This subdev2 represents IMX477 sensor component.
